# 酒店房态与入住协调智能体系统 · 技术架构方案

> 版本 v1.0 ｜ 2026-10-30 ｜ 状态：选型已确认，待开工
> 技术栈：FastAPI（异步）+ Python 3.11+ + PostgreSQL/pgvector + OpenAI 兼容 LLM API
> 角色：普通员工（问答 + 入住协同）、管理员（管理房态 + 查看记录）
> 关联文档：业务口径见 [业务挖掘-发现报告](业务挖掘-发现报告.md)，规则与闸门见 [设计架构](设计架构.md)，本文只讲「智能体系统」如何落地。

## 一、两个已确认的选型

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 向量库 | **PostgreSQL + pgvector（业务与向量同库）** | 单库单事务、运维最简；审计与向量可同库联查；规模（180 间房、数千制度块）远未到独立向量库的门槛 |
| LLM 接入 | **OpenAI-compatible 协议抽象** | DeepSeek / Qwen / GPT 均兼容该协议，改 `LLM_BASE_URL + LLM_MODEL` 即切换供应商，业务代码零改动 |

## 二、四层架构

```
┌───────────────────────────────────────────────────────────┐
│ L1 入口层（FastAPI 异步）                                    │
│   · 认证鉴权：JWT + 双角色 RBAC（staff / admin）             │
│   · 对话接口：SSE 流式（/api/chat/stream）                   │
│   · 管理接口：房态变更、记录查询、制度文档管理（管理员专用）    │
│   · 中间件：脱敏（房号/工号/手机号）、审计埋点、统一异常       │
└──────────────────────────┬────────────────────────────────┘
                           ▼
┌───────────────────────────────────────────────────────────┐
│ L2 服务层（确定性业务逻辑——智能体的"地基"）                   │
│   · room_service    三态投影（占用×清洁×封锁）+ 缺口检出     │
│   · handoff_service 管理单校验 R1–R6                        │
│   · gate_service    具名确认闸门 / 状态机（OOO 解除硬拦截）  │
│   · audit_service   append-only 审计链（岗位 + 哈希）        │
│   ※ 核心原则：LLM 只能"起草/解释"，生效必须过确定性校验+闸门 │
└──────────────────────────┬────────────────────────────────┘
                           ▼
┌───────────────────────────────────────────────────────────┐
│ L3 智能体编排层（Agent Orchestration）                       │
│   · router        意图路由：制度问答 / 房态查询 / 协同起草    │
│   · orchestrator  编排主循环（简化 ReAct，最多 3 步工具调用） │
│   · tools         工具注册：查房态 / 起草管理单 / 查记录      │
│                   （工具只调 L2 服务，不直连数据库）          │
│   · rag           制度文档：加载 → 分块 → 向量化 → 召回 → 引用│
│   · llm           Provider 抽象 + OpenAI 兼容实现 + 工厂     │
│   · guardrails    越权拦截、引用必带条款号、幻觉兜底          │
└──────────────────────────┬────────────────────────────────┘
                           ▼
┌───────────────────────────────────────────────────────────┐
│ L4 数据模型层                                                │
│   · PostgreSQL：users / sessions / messages /               │
│     policy_documents / policy_chunks(vector) /              │
│     handoff_drafts / audit_log                              │
│   · Redis（可选，二期）：会话缓存与限流                      │
└───────────────────────────────────────────────────────────┘
```

**分层的核心决策**：确定性规则放 L2、智能体放 L3，**LLM 永不直接写业务库**——它产出的管理单只是 `draft`，状态机 `draft → pending_review → confirmed` 走完闸门才生效。这是防止幻觉变成业务事故的唯一可靠手段。

## 五、第一周最小验证目标（Week-1 MVP）

**一句话**：用真实 LLM + 真实数据库，端到端跑通**一条问答链路 + 一条协同链路**，验证四个风险假设。

| # | 链路 | 验证什么 |
| --- | --- | --- |
| 1 | 员工问「退房后多久能标可售？」→ 检索**一份**真实制度文档 → LLM 带**条款号引用**作答 | RAG 链路通不通、引用是否可信 |
| 2 | 员工问「8203 现在能卖吗」→ 意图路由到房态工具 → 返回三态投影结果（VC/VI/OOO…）而非模型编造 | 工具调用 vs 幻觉 |
| 3 | 员工说「给 8203 起草交接单」→ LLM 生成草稿 → **故意把 VC 房写成可售** → R1 校验拦截并退回 | 确定性护栏是否真的拦得住 |
| 4 | 管理员登录 → 查到这条被拦截的记录（含岗位与哈希）→ 确认草稿生效 | 双角色权限隔离 + 闸门闭环 |

**验收标准**：`docker-compose up` 一键起（app + pgvector），4 条链路各跑通一次，`pytest` 通过三态投影与 R1–R6 单测。

**第一周明确不做**：流式输出打磨、重排模型（rerank）、多版本制度管理界面、Redis 限流、管理员房态 CRUD 全套——全部只留接口占位。

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 幻觉编造房态/制度 | 房态只来自工具调用；制度回答必须带条款号引用，无引用则回答"未在制度库中找到依据" |
| 越权操作（员工触发管理员动作） | 工具层做角色白名单，越权直接拒绝并审计 |
| 敏感信息进对话/日志 | 入口层统一脱敏，messages 落库前二次校验 |
| 供应商切换成本 | OpenAI 兼容抽象 + 环境变量切换，embedding 维度不同则重建索引（脚本支持） |
| 试点期接口只读（f32） | 回写走受控通道 + 人工闸门，与既有《设计架构》方案一致 |
