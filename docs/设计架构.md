# 酒店房态与入住协同系统 · 设计架构文档

> 版本 v1.0 ｜ 日期 2026-10-30 ｜ 依据 HRSC 仓库《业务挖掘-发现报告》《行业分析》《需求清单-一页纸》｜ 目标读者：研发团队 / 甲方技术评审

## 一、架构总览

本系统定位为**房态协同层**：不替代现有 PMS，通过只读接口统一「已清扫 / 已查房 / 可售」三态口径，以确定性校验 + 最少人工闸门消除前台误判。整体采用**模块化单体**——单库、单部署单元，内部按业务域切分为清晰模块，为未来拆分留缝。

```
┌─────────────────────────────────────────────────────────────┐
│                        接入层（只读）                          │
│   PMS 房态接口  │  客房任务平台  │  渠道订单库（只读）            │
└───────────────┬─────────────────┬───────────────────────────┘
                ▼                 ▼
┌─────────────────────────────────────────────────────────────┐
│                    房态协同服务层（单体）                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ 三态投影  │ │ 缺口检出  │ │ 交接单    │ │ 审计链    │        │
│  │ 模块     │ │ 模块     │ │ 模块     │ │ 模块     │        │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────────────┐     │
│  │ 人工闸门  │ │ 受控回写  │ │ 脱敏层（送模型前统一处理）│     │
│  └──────────┘ └──────────┘ └──────────────────────────┘     │
└───────────────┬───────────────────────────────────────────────┘
                ▼
   ┌────────────────────────────┐
   │  数据层：MySQL（单库）       │
   │  room_state / state_event / │
   │  handoff / audit / gate     │
   └────────────────────────────┘
```

## 二、核心数据模型

房态**不是单字段**，而是三个正交维度 + 事件日志：

### 2.1 三态投影维度

| 维度           | 取值                        | 来源系统       | 说明                |
| ------------ | ------------------------- | ---------- | ----------------- |
| 占用 occupancy | vacant / occupied         | PMS        | 是否在住              |
| 清洁 clean     | dirty / clean / inspected | 客房任务平台     | 已清扫 vs 已查房        |
| 库存封锁 block   | none / OOS / OOO          | PMS + 客房调度 | OOO 扣减可售，OOS 保留展示 |

### 2.2 投影规则（确定性，非模型判断）

| 组合               | 投影码 | 可售 | 含义                    |
| ---------------- | --- | -- | --------------------- |
| block=OOO        | OOO | 否  | 维修房（库存扣减）             |
| block=OOS        | OOS | 是  | 停用房（可售但需提示原因）         |
| occupied + clean | OC  | 否  | 在住·已整理                |
| occupied + dirty | OD  | 否  | 在住·待整理                |
| clean=inspected  | VI  | 是  | 可售                    |
| clean=clean      | VC  | 否  | 已清扫·待查房（**前台不得标可入住**） |
| clean=dirty      | VD  | 否  | 脏房                    |

### 2.3 事件日志（state_event）

每次状态流转追加一条不可变记录：

```
state_event { id, room_no, dim(occupancy|clean|block), from, to,
              actor_role, actor_hash, reason, occurred_at, source }
```

作用：可回答「谁在何时把状态改成了什么」，支撑审计重建（REQ-5 的误判口径自动统计即基于此表）。

## 三、模块职责

| 模块   | 职责                   | 关键规则                        |
| ---- | -------------------- | --------------------------- |
| 三态投影 | 聚合三源数据 → 输出统一房态码     | 确定性映射，规则即代码                 |
| 缺口检出 | 比对投影结果与三岗口径 → 标记缺口   | VC 未查房 / OOO 在售 / 无具名接收     |
| 交接单  | 自动起草 + 确定性校验         | 必填字段、可售冲突、40 字限制            |
| 人工闸门 | 四类动作强制具名确认           | 异常接收 / OOO 解除 / 交接确认 / 影像删除 |
| 受控回写 | 仅经确认的数据回写            | 回写一个动作完成，绝不静默               |
| 审计链  | append-only 记录，岗位+哈希 | 不留姓名、手机号等个人信息               |
| 脱敏层  | 送模型/日志前统一处理          | 房号→[房号]、工号→[工号]、手机→[手机号]    |

## 四、关键流程

### 4.1 房态同步（快照式，每日两次）

```
三源只读拉取 → 三态投影 → 缺口检出 → 有缺口? 
  ├─ 否 → 更新统一视图
  └─ 是 → 异常看板告警 → 具名复核补录 → 重新投影
```

> 试点阶段采用**快照式同步**（每日两次更新已授权状态，见 f34），不承诺实时流。实时推送与 OTA 直连均为范围外，接口层预留 ChannelConnector 接缝。

### 4.2 交接单起草与校验

```
选中房间 → 自动起草(三态投影+缺口) → 确定性校验(R1–R6) 
  ├─ 不通过 → 退回补录（标注冲突字段）
  └─ 通过 → 具名接收人签收 → 受控回写 → 审计留痕
```

### 4.3 维修房（OOO）解除封锁

```
OOO 解除请求 → 强制异味复查（必填证据）→ 人工复核 → 具名确认 → 恢复库存
```

> 异味复查结果为**必填证据字段**，缺失即不允许库存恢复——这是确定性硬拦截，不交给模型置信度判断。

## 五、校验规则（确定性，不交给模型）

| 编号 | 规则                |
| -- | ----------------- |
| R1 | 可售状态必须等于三态投影结果    |
| R2 | 异常必须有具名接收人        |
| R3 | 维修房 OOO 不得出现在可售清单 |
| R4 | 下一步动作不超过 40 字     |
| R5 | 审计只记岗位与哈希，不留个人信息  |
| R6 | 查房影像保留 90 天，到期清理  |

## 六、审计与隐私

- **审计链**：`audit_entry { at, actor_role, action, room_no, before, after, hash }`，append-only，哈希可验证完整性；
- **脱敏**：房号 / 工号 / 手机号在送模型、写日志前统一替换为占位符；
- **隐私边界**：客人身份与房号限制访问，隐私信息不进入公共任务群（f40）；影像 90 天到期清理（f43，期限待甲方书面确认）。

## 七、部署与规模

- **部署**：单体单实例，MySQL 单库；前端为无构建步骤的静态 SPA，可由任意静态服务器承载；
- **规模**：144–180 间房、几十个员工终端、周末 18:00–21:00 高峰——无需读写分离、消息队列或缓存集群；
- **预留缝**：`tenant_id` 字段（多店扩展）、`ChannelConnector` 接口（OTA 直连扩展）、事件日志表（未来实时流改造）。

## 八、技术栈建议

| 层   | 选型                        | 理由                    |
| --- | ------------------------- | --------------------- |
| 前端  | 原生 HTML/CSS/JS（无框架）       | 团队小、免构建，Demo 已用此栈验证   |
| 后端  | 单体（Python/FastAPI 或 Node） | 与现有人力匹配，模块化单体够用       |
| 数据库 | MySQL                     | 事务一致性（库存扣减、审计 append） |
| 集成  | 只读 REST 适配器 + 受控回写通道      | 符合 f32 接口约束           |

## 九、与参考项目的对齐

- 三态生命周期（dirty/clean/inspected）→ 对齐 `voyant-travel/pms`；
- OOO 库存扣减 → 对齐 `voyant-travel/pms` 的 maintenance block；
- 状态机前置校验 → 对齐 `LS3213/NexusStay-OS`；
- 现场一个动作回写 → 对齐 `olegromanchuk/hotelito` 的电话功能码理念。

## 十、范围外（明确不做）
