# 开源项目参考

> 为补强「行业可行性（Industry）」来源，选取公开可查的开源酒店管理系统与 FDE 方法论仓库做横向比对。比对目的不是照搬代码，而是回答：同类问题行业内怎么解？哪些设计可以直接借鉴？哪些前提在我们场景里不成立？
>
> 所有链接与描述基于各仓库 README，未做代码级审计；核对日期 2026-10-23。

## 二、三个可借鉴的关键设计

### 1. 房态不是单字段，而是「状态 + 事件日志」双结构

voyant-travel/pms 与 HotelOpsManager 都把 dirty / clean / inspected 作为独立可读状态，且查房是一个显式事件而非隐含假设。这直接对应 REQ-1：本项目把三态压成一个字段，前台只能靠猜。Demo 中的三态投影（`src/engine.js` 的 `projectStatus`）即按此实现。

### 2. 维修房（OOO）应作为「库存扣减」而非「另一个房态标签」

voyant-travel/pms 的 maintenance block 会直接减少可售库存，从而在排房与渠道侧就排除该房间。对照 REQ-3：本项目「维修房解除封锁」不应只是改标签，而要同步影响可售清单——且解除封锁必须带强制复查证据，不得自动放行。

### 3. 现场回写必须「一个动作完成」，不能要求人离开现场

hotelito 用房间电话功能码回写房态，是极简但真实的现场约束体现。这与前台接待员林亦舟所述「高峰期只能使用现有终端，离开现场补录会延误处理」（f12/f13）完全一致：任何要求一线多走一步的方案，高峰期必被绕过。

## 三、与本项目的差异及不适用之处

开源项目的成熟度不能直接等同于本项目可行性。以下差异项也是「Industry 来源仍不能算已收敛」的原因：

| 参照做法 | 成立的前提 | 本项目现状 |
| --- | --- | --- |
| 三态独立建模 | PMS 具备写权限与字段扩展能力 | 现有接口仅可读，字段拆分需 PMS 侧改造与审批（f32） |
| 维修封锁扣减库存 | 库存扣减与渠道同步在同一事务内 | PMS、客房任务平台、渠道订单库三套系统权限独立、无统一视图（f30） |
| 任务自动生成（cron / 实时推送） | 系统可承载实时事件 | 试点计划每天两次更新已授权状态（f34），本质是快照而非实时流 |
| 查房电子签核 + 照片留证 | 可存储影像且符合隐私要求 | 影像留存与 90 天期限规则尚待确认（f43），隐私信息不得进入公共任务群（f40） |

**结论**：参照项目可以证明「三态拆分 + 维修封锁独立建模」在工程上是常规做法，但不能证明本项目在当前接口条件与权限约束下可行。Industry 来源仍标记为「部分补强」。

## 四、对候选需求的修正建议

- **REQ-1** 补充验收细则：借鉴 NexusStay-OS 的前置状态校验，把「状态流转是否带前置状态与操作人」纳入只读核查项，而不只核查字段是否存在；
- **REQ-2** 增加可用性约束：交接单字段数量需经现场计时验证（建议以不超过现有单据填写时长为上限），否则高峰时段必被绕过；
- **REQ-3** 做硬拦截：把「异味复查结果」设为解除封锁的必填证据字段，缺失即不允许库存恢复——这是确定性校验，不应交给模型置信度判断；
- **REQ-5** 借鉴事件日志口径：误判计数可基于状态事件日志（谁在何时把状态改成了什么）自动统计，减少人工判定的口径争议；但事件日志是否可取，取决于 REQ-1 的核查结果；
- **方法论层面**：参照 fde-simulation 的 Agent 形态目录，把「房态解释」定位为「汇总 + 审核」组合，把「交接提醒」定位为「路由」，均不涉及自动开锁或身份认证等高危动作。
