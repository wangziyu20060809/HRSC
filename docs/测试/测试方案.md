## 一、测试目标

被测系统要解决的是**一个具体的现场断点**：客房部把房间标成「已清扫」，前台把它当成「可入住」，
客人到店后平均等待 38 分钟，且全程无记录、无法复盘。因此测试不只验证「接口能通」，而要回答四个问题：

| 编号 | 待验证命题 | 对应量化门限 |
| --- | --- | --- |
| G1 | 「已清扫」与「可售」在系统里是否真的分开，前台能否绕过 | 绕过尝试拦截率 100%，拦截后必须给出原因与替代房 |
| G2 | 结论权与执行权是否分离，越权是否被拒 | 越权请求 100% 返回 403 + 业务码 40301 |
| G3 | AI 只读、写操作是否必须人工确认 | 提案落 `pending` 率 100%，无一条自动执行 |
| G4 | 依赖件（大模型 / 知识库 / 数据库）故障时是否降级而非崩溃 | 降级响应 ≤ 90 s，业务读接口仍可用，健康检查仍 ok |

## 二、被测对象与范围

### 2.1 系统构成

| 层 | 内容 |
| --- | --- |
| 接入 | FastAPI + Jinja2 服务端渲染，原生 JS（无构建步骤），SQLite（WAL） |
| 业务内核 | 房态状态机：**7 个状态 / 10 条受控迁移**，全部集中在一个 `apply()` 入口 |
| 权限 | JWT（HS256）+ PBKDF2（12 万轮）+ 岗位权限矩阵 `TRANSITION_ROLES` |
| Agent | 预取（确定性代码）→ 生成（≤ 4 步工具循环）→ 校验（5 条护栏，命中降级为 `guarded`） |
| 工具 | 11 个：7 个只读 + 4 个 `propose_*`（只落 pending 提案） |
| 知识库 | 5 篇制度 / 19 个段落切片（≤ 320 字）/ BM25（中文二元组）+ 256 维哈希向量 RRF |
| 规模基线 | 24 间房、628 条历史事件流水、4 个岗位账号、14 条待办任务 |

### 2.2 状态机（测试的判定基准）

```
dirty(待清扫) → cleaning(清扫中) → clean(已清扫待查房) → inspecting(查房中) → ready(可售) → occupied(在住)
                                                                                    ↘ rework → dirty
任意可售前状态 → blocked(维修中) → dirty
```

**关键设计：`clean` 与 `ready` 强制分离**，`check_in` 的 `from` 只有 `ready`。这既是产品核心，也是本次测试的第一判定基准。

### 2.3 岗位与结论权

| 动作 | front 前台 | house 客房 | qa 质检 | admin 运营 |
| --- | :-: | :-: | :-: | :-: |
| start_cleaning / finish_cleaning | — | ✅ | — | ✅ |
| start_inspection | — | ✅ | ✅ | ✅ |
| **pass_inspection / fail_inspection（下结论）** | **—** | **—** | **✅** | ✅ |
| check_in / check_out（执行） | ✅ | — | — | ✅ |
| block（报修） | ✅ | ✅ | ✅ | ✅ |
| unblock / rework | — | ✅ | ✅ | ✅ |
| 知识库、账号、阈值 | — | — | — | ✅ |

### 2.4 范围内 / 范围外

- **范围内**：接口契约与业务码、状态迁移守卫、入住闸门、岗位权限、Agent 护栏与提案确认、故障降级、页面关键路径。
- **范围外**（明确不做，避免用结论误导验收）：并发压测与容量规划、专业渗透测试、多浏览器兼容矩阵、移动端适配、真实大模型效果评测（仅验证降级与引证行为）。

## 三、测试策略

采用**三层证据链**，每层各自可复核，避免只给「通过」两个字：

| 层 | 手段 | 产出 | 解决什么 |
| --- | --- | --- | --- |
| L1 接口矩阵 | `tools/test_matrix.py`（httpx，四岗位独立会话） | 53 条用例的 `状态码 + 业务码 + 耗时 + 判定`，落 `测试矩阵结果.json/.md` | 可重复、可量化、可回归 |
| L2 页面实拍 | Edge headless + CDP（`tools/capture.js`） | 25 张截图，含「接口证据面板」（请求 / 状态码 / 返回体均为真实调用） | 证明「用户看到的就是这个」 |
| L3 文档核对 | 访谈事实 f00–f55 与需求追溯矩阵比对 | 指标口径与验收标准逐条对齐 | 防止系统做对了、口径却跑偏 |

### 3.1 五类场景的设计方法

| 场景 | 设计方法 | 用例数 | 判定标准 |
| --- | --- | --- | --- |
| 正常 | 主流程端到端串联（清扫→查房→可售→入住→退房）+ 关键只读能力 | 15 | 全链路状态正确、任务自动衍生、助手有依据 |
| 边界 | 等价类 + 边界值（住晚 0/31、房号格式、空查询、800 字超长输入） | 12 | 越界一律受控拒绝，不产生脏数据 |
| 对抗 | 提示词注入、伪造制度出处、SQL/XSS 注入串、绕过闸门、伪造动作、强制跳过确认、并发覆盖 | 9 | 拒绝或降级，且不得出现「已执行」类表述 |

| 故障 | 模型 Key 失效、知识库清空、数据库写锁、服务不可达 | 5 | 降级可读、受控 500、不挂死 |

### 5.3 缺陷与处理

| 编号 | 现象 | 定性 | 处理 |
| --- | --- | --- | --- |
| D1 | 岗位越权的 HTTP 状态码是 400 而不是 403：业务码写的是 `40301`，但 `ApiError` 默认 `status=400`，导致「越权」和「参数错」在状态码上无法区分 | 缺陷（已修复） | `core/errors.py` 增加 `status_for(code)`，按错误码前三位派生 HTTP 状态（40001→400 / 40301→403 / 40901→409 / 50001→500），并保留显式覆盖。修复后 P02/P03/P06 由 400 变为 403，矩阵重跑 53/53 |
| D2 | 后端 `pass_inspection` 只拦截「显式 `false`」的检查项，缺省的检查项视为通过——若绕过页面直接调接口，可提交 2/6 项就通过查房 | 已知弱项（未修复） | 页面层已强制 6 项全勾（`staff.js`），服务端未做完整性校验。列入遗留 I1，建议下版补 `INSPECTION_ITEMS` 全量校验 |
| D3 | 知识库索引是**进程内缓存**，跨进程直接改库（sqlite 删除文档）后，检索仍返回旧结果 | 测试方法约束（非产品缺陷） | 故障用例改为「通过 `DELETE /api/kb/docs/{id}` 清空」，走产品自身入口即可正确失效缓存。生产多实例部署时需在变更后调用 `POST /api/kb/reindex`，已写入运行手册 |
