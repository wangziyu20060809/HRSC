# 架构说明 · 房态与入住协同 MVP

> 本文回答三个问题：**工程怎么分层**、**Agent 框架怎么保证不乱说话不乱改数据**、**知识库怎么让口径可查可改**。
>
> 阅读顺序建议：先看「一、问题与取舍」，再看「二、工程架构」，最后看「三、Agent 框架」与「四、知识库」。

---

## 一、问题与取舍

### 1.1 从访谈里读出的断点

访谈（`访谈记录-turn-2` / `turn-4`）与客户简报反复出现同一段叙述：

> 客房部在系统里标了「已清扫」→ 前台看到「已清扫」就当成「可入住」→ 客人到店，房还没查 → 客人在大堂等。

拆开看是三个独立缺陷：

| 缺陷 | 本质 | 后果 |
| --- | --- | --- |
| 口径缺失 | 「已清扫」与「可售」被当成一件事 | 房态错误 24 次/周（基线） |
| 无强制闸门 | 前台可以在任何状态点开房 | 错误不报错，只在下一位客人到店时暴露 |
| 时效不可见 | 没人统计「已清扫 → 可售」用了多久 | 高峰入住等待 38 分钟（基线）无人归因 |

### 1.2 三条设计原则

1. **不猜房态**。AI 在这套系统里不负责判断「房间到底能不能卖」，只负责**把系统已经确定的事实讲清楚**。判断权在状态机里，是确定性代码。
2. **结论权与执行权分开**。前台能办入住、能报修，但**没有**「把已清扫改成可售」的按钮；查房结论只能由质检下。这是权限设计问题，不是提示词问题。
3. **AI 只提案，人执行**。所有写操作走「提案 → 人工确认 → 再校验 → 执行」四步。模型再强也改不了房态。

### 1.3 MVP 的边界（来自客户简报）

- 只做**只读核对与人工交接**，不做自动放行、不替人下查房结论；
- 不承诺收益数字：`38 分钟 → 15 分钟` 是管理层给的**目标**，MVP 交付的是**可自动计算的代理指标**（已清扫→可售均时与 P90、拦截次数），验收需门店按节点补测；
- 不做 PMS / 门锁 / 工单系统的真实对接，接口按「可替换适配器」设计（见 §5.3）。

## 二、工程架构

### 2.1 分层与依赖方向

```
                    ┌──────────────────────────────┐
   浏览器 ──────────▶│  templates/ + static/        │  三个页面，无构建步骤
                    └──────────────┬───────────────┘
                                   │ fetch / JSON
                    ┌──────────────▼───────────────┐
                    │  api/    鉴权、参数校验        │  薄接口层
                    └──────┬───────────────┬───────┘
                           │               │
              ┌────────────▼───┐    ┌──────▼────────┐
              │  domain/       │    │  agent/       │  Agent 框架
              │  状态机 / 指标  │◀───│  预取生成校验  │
              └────────┬───────┘    └──────┬────────┘
                       │                   │
                       │            ┌──────▼────────┐
                       │            │  kb/  检索     │
                       │            └──────┬────────┘
              ┌────────▼───────────────────▼───────┐
              │  core/  db · security · errors     │
              └────────────────────────────────────┘
```

依赖单向向下，**不允许反向 import**：

- `domain/` 不 import FastAPI、不 import LLM、不 import kb —— 所以 41 个测试里 25 个是纯业务规则，跑一次 40 秒，不需要起服务、不需要密钥；
- `agent/` 可以 import `domain/` 与 `kb/`，但不能绕过 `domain/state_machine.transition()` 直接写 `rooms` 表；
- `api/` 只做三件事：鉴权、参数校验、把 `ApiError` 转成统一错误响应。业务判断一律下沉。

### 2.2 为什么把状态机做成「业务内核」

`domain/state_machine.py` 是本项目唯一能改房态的地方。页面、接口、Agent 工具三条入口最终都调用同一个 `transition()`：

```python
transition(room_no, action, actor, role, payload) -> dict
#  1. 查迁移表：action 是否存在、当前状态是否在 from 里
#  2. 岗位校验：TRANSITION_ROLES[action] 是否包含 role
#  3. 守卫：pass_inspection 必须六项检查全过；block 必须有原因；rework 必须有说明
#  4. 写 rooms + 追加 room_events + 按需建/关任务
#  5. 返回新状态、允许的下一步动作、超时标记
```

**七个状态、十条迁移**：

| 状态 | 中文 | 可售 | 说明 |
| --- | --- | --- | --- |
| `dirty` | 待清扫 | ✗ | 退房后或待整理 |
| `cleaning` | 清扫中 | ✗ | 客房部作业中 |
| `clean` | 已清扫待查房 | ✗ | **关键节点：已清扫 ≠ 可售** |
| `inspecting` | 查房中 | ✗ | 质检核对中 |
| `ready` | 可售 | ✓ | **唯一允许入住的状态** |
| `occupied` | 在住 | ✗ | 客人已入住 |
| `blocked` | 维修中 | ✗ | 须记录原因与责任岗位 |

| action | from | 允许岗位 |
| --- | --- | --- |
| `start_cleaning` | dirty | house, admin |
| `finish_cleaning` | cleaning | house, admin |
| `start_inspection` | clean | qa, house, admin |
| `pass_inspection` | inspecting | **qa, admin** |
| `fail_inspection` | inspecting | **qa, admin** |
| `check_in` | **ready** | front, admin |
| `check_out` | occupied | front, admin |
| `block` | dirty / cleaning / clean / ready | front, house, qa, admin |
| `unblock` | blocked | house, qa, admin |
| `rework` | clean / inspecting / ready | qa, house, admin |

`check_in` 的 `from` 只有 `ready` 一条——**这就是闸门本身**。它不依赖前端按钮是否隐藏，也不依赖提示词是否写了「不要放行」，是在内核里写死的。

### 2.3 入住闸门（`checkin_gate`）

前台输入房号，先过闸门再谈输名字：

```
checkin_gate(room_no) →
  can_checkin: false
  reason:      "已清扫但查房未完成，不能办理入住"
  owner:       "质检"          # 责任岗位，指到人而不是指到部门
  eta_min:     15              # 预计还需多久
  alternatives: ["801","1001","804"]   # 立刻能卖的替代房
```

替代房是刻意设计的：**拦截必须给出口**，否则前台的现实选择就是绕过系统。有了替代房，拦下 803 不等于让客人站着等。

### 2.4 数据模型（14 张表）

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `users` | 账号 | PBKDF2-HMAC-SHA256，12 万轮 + 随机盐 |
| `rooms` | 房间当前状态 | `state` 只能在 7 个枚举内；`block_reason` 由守卫强制 |
| `room_events` | 房态流水 | **只追加，不更新不删除**，时效指标的唯一原料 |
| `tasks` | 待办（查房 / 清扫 / 维修） | 迁移自动创建，避免人手抄 |
| `checkins` | 入住记录 | 与 `ready → occupied` 迁移一一对应 |
| `interventions` | 拦截留痕 | 每次被闸门拦下都落一条，即「房态错误」的替代观测 |
| `handovers` | 交接班记录 | 草稿可编辑，提交后归档 |
| `audit_log` | 操作审计 | 谁在什么时候改了什么，含请求摘要 |
| `kb_docs` / `kb_chunks` | 知识库 | 切片与向量持久化，可重建 |
| `agent_sessions` / `agent_messages` / `agent_actions` | 助手会话、消息、提案 | 提案有 `pending/confirmed/rejected` 三态 |
| `settings` | 阈值与提示词 | 改完即时生效（无缓存） |

SQLite + WAL，`data/mvp.db`。选它的理由不是「省事」，是**验收可取证**：单文件可打包给客户，`room_events` 与 `interventions` 能直接算出「本周拦了几次、平均多久」。

### 2.5 接口清单（34 个 API + 5 个页面）

| 分组 | 端点 | 说明 |
| --- | --- | --- |
| 页面 | `GET /` `/login` `/staff` `/admin` | 服务端渲染外壳，数据由 JS 拉取 |
| 认证 | `POST /api/auth/login` `logout`，`GET /api/auth/me` | JWT 放 HttpOnly Cookie，8 小时 |
| 房态 | `GET /api/rooms`，`GET /api/rooms/{no}` | 看板与单房详情（含 allowed_actions） |
| 迁移 | `POST /api/rooms/{no}/transition` | **唯一写房态入口**，内部走 `transition()` |
| 入住 | `POST /api/rooms/{no}/checkin`，`GET /api/checkin/gate` | 闸门先查后办 |
| 看板 | `GET /api/dashboard` | 计数、超时、趋势、指标 |
| 任务 | `GET /api/tasks`，`POST /api/tasks/{id}/action` | 认领 / 完结 |
| 交接 | `GET /api/handover/draft` `history`，`POST /api/handover` | 自动生成草稿 |
| 助手 | `POST /api/agent/chat`，`GET /api/agent/history` `status` `actions` | 对话与提案 |
| 提案 | `POST /api/agent/actions/{id}/confirm` `reject` | 人工确认闸门 |
| 知识库 | `GET/POST/DELETE /api/kb/docs`，`POST /api/kb/reindex` `search` | 管理端维护 |
| 管理 | `/api/admin/audit`、`settings`(GET/PUT)、`users`(GET/POST)、`users/{id}/toggle`、`users/{id}/reset-password`、`agent-stats` | 审计、阈值、账号 |

错误统一为 `{"error": {"code": "...", "message": "..."}}`，`code` 是机器可读枚举（`FORBIDDEN_ROLE`、`INVALID_TRANSITION`、`GUARD_FAILED`…），前端据此决定是弹窗还是内联提示。

### 2.6 前端

三个页面（`login` / `staff` / `admin`），手写 CSS + 原生 JS，**无构建步骤**——客户现场打开浏览器就能验收，不需要 `npm install`。状态全部由 `GET /api/*` 拉取，页面本身不嵌业务数据。

员工端五个区：房态看板（24 间房按状态着色）、入住办理（含闸门结果）、查房队列（超时置顶）、交接班（草稿一键生成）、值班助手（对话 + 提案卡）。

管理端五个区：概览（拦截趋势 SVG + 时效分布 + 状态构成）、知识库（在线编辑 + 检索测试）、助手配置（提示词与阈值）、审计（操作流水）、账号。

## 三、Agent 框架

### 3.1 三段式：预取 → 生成 → 校验

```
员工提问
   │
   ├─① 预取（确定性代码，0 ms 模型开销）
   │    问句里有房号 → 查房态 + 闸门结论 + 替代房
   │    问「有房吗」  → 查可售列表（按房型过滤）
   │    问指标/统计   → 查 overview()
   │    问规则/口径   → 检索知识库 top-k
   │    问交接        → 生成交接摘要
   │  ↓ 拼成【当班数据】【可用制度片段】塞进系统消息
   │
   ├─② 生成（模型，最多 4 步工具循环）
   │    模型只负责：还缺什么数据（可继续调工具） + 把结论写成员工听得懂的话
   │    可用工具 11 个：7 只读 + 4 只提案
   │
   └─③ 校验（确定性代码）
        任一条命中 → 判不合格 → 改用规则答案，界面标 `guarded` 并说明原因
```

**为什么先预取再让模型说话**：让模型自己去「想起来要查房态」，十次里有两次会忘，而忘的那两次正好是高峰。预取把「该查什么」变成代码里的 if-else，模型只做语言组织，稳定性从「大概率对」变成「结构性对」。

### 3.2 工具清单（11 个）

| 类型 | 工具 | 作用 |
| --- | --- | --- |
| 只读 | `list_rooms` | 按状态/房型/楼层筛选房间 |
| 只读 | `get_room` | 单房详情：状态、已保持时长、能否入住、下一步、替代房 |
| 只读 | `find_available_rooms` | 可售房列表（支持房型） |
| 只读 | `list_pending_inspections` | 待查房队列，超时优先 |
| 只读 | `get_metrics` | 可售率、时效、拦截、超时、任务 |
| 只读 | `search_knowledge` | 制度检索，返回 `ref` + 片段 |
| 只读 | `get_shift_summary` | 交接摘要（可直接复制进交接单） |
| 写（提案） | `propose_start_inspection` | 提案：对某房发起查房 |
| 写（提案） | `propose_mark_ready` | 提案：提交可售（仅质检可用） |
| 写（提案） | `propose_block_room` | 提案：报修停用（须带原因） |
| 写（提案） | `propose_checkin` | 提案：办入住（须带客人姓名） |

**写工具命名刻意用 `propose_` 前缀**，函数签名里也没有「执行」这个动作——工具只能落一条 `agent_actions(status='pending')`，执行发生在 `POST /api/agent/actions/{id}/confirm`，那条路径会**重新跑一遍岗位校验和状态守卫**。这意味着：即使模型幻觉出「给 803 办入住」，也只是一张待确认卡片；即使有人伪造 confirm 请求，岗位不对仍然 403。

### 3.3 校验规则（护栏）

`_validate(answer, facts, pre, trace)` 返回 `(ok, reason)`，命中即降级：

| # | 规则 | 拦的是什么 |
| --- | --- | --- |
| 1 | 引用的《文档名》必须在 `kb_docs` 或本轮检索结果里 | 编造制度出处 |
| 2 | 「已为你发起/已办理…」但本轮没有生成任何提案 | 嘴上答应、实际没动作 |
| 3 | 「拦截 N 次」「可售 N 间」「待查房 N 间」「超时 N 间」的数字必须命中本轮查询值 | 数字幻觉 |
| 4 | 提到的房号必须在本轮查过（正文内的引号内容先剔除） | 凭空说「803 可以入住」 |
| 5 | 出现指标数字但本轮没查指标 | 凭印象报数 |

不合格时的处理不是「再问模型一次」，而是**直接换成规则答案**（`agent/runtime.py::_fallback`），并在响应里带 `mode="guarded"` 与 `note` 说明原因。宁可答案朴素，不可答案骗人。

### 3.4 无密钥降级

`config.llm_ready()` 为假时，同一套工具交给规则规划器：按意图槽位（房号 / 可售 / 指标 / 规则 / 查房 / 交接 / 维修 / 动作）分别编排，`mode="fallback"`。功能不减，只是话术不如模型自然。**这是有意的**：客户演示环境不一定有网、有 Key、有预算，降级路径必须是完整可用的。

### 3.5 观测

每次对话落 `agent_messages`（问、答、模式、延迟、引用、trace）与 `agent_actions`。管理端「助手统计」给出：调用量、`llm` / `guarded` / `fallback` 三态占比、平均延迟、提案确认率。护栏触发率高于 15% 说明提示词或工具描述需要改——这是可运营的指标，不是玄学。

## 四、知识库

### 4.1 内容

5 篇制度（`kb/docs/*.md`），覆盖访谈里出现频次最高的口径争议：

| 文档 | 回答什么问题 |
| --- | --- |
| 01 房态口径与三态定义 | 「已清扫」到底算不算能卖 |
| 02 查房标准与检查项 | 六项检查是什么、不通过怎么返工 |
| 03 入住办理与可售闸门 | 什么状态能开房、拦下后怎么办 |
| 04 超时升级与交接规则 | 多久算超时、升级给谁、交接交什么 |
| 05 异常处置与维修房管理 | 报修、停用、恢复可售的路径 |

### 4.2 切片与检索

- **切片**：按段落聚合成 ≤320 字，保留 `§章节` 与文档标题，引用时能回到原文；
- **检索**：两路并行再融合
  - BM25（中文二元组分词）：对「已清扫」「可售」「查房」这类短术语最准；
  - 256 维哈希向量（字符二元组 + 稳定 md5 哈希）：补口语化问法（「房间弄好了能开吗」）；
  - RRF（k=60）融合两路排名，取 top-k；
- **引用**：返回 `{doc_title, section, ref, text}`，`ref` 形如 `03-入住办理与可售闸门 §2 第 3 段`，员工可以照着回原文核对。

**为什么不直接上 embedding 模型**：MVP 要的是**离线、确定性、可回归**。哈希向量在 19 个切片的小库上召回已经够用（单测覆盖 8 组问法），且零费用零延迟。生产替换点只有一个函数：

```python
# kb/embedder.py
def embed(text: str) -> list[float]:   # 换成 text-embedding-v3，接口不变
```

### 4.3 可运营

管理端能在线改文档、加文档、删文档、重建索引，并带一个「检索测试」框——改完口径立刻用真实问句验证召回，不用重启服务。改完提问立刻按新口径回答（提示词与文档都存库、每请求读取，无缓存）。

## 五、落地与演进

### 5.1 部署

单进程 uvicorn，SQLite 单文件，无外部依赖（除可选的模型 API）。适合单店试点：一台小机器或门店现有服务器即可，数据不出店。多店时把 `core/db.py` 换成 PostgreSQL、`rooms` 加 `hotel_id`，其余不动。

### 5.2 测试策略

41 项单测，三层：

| 层 | 数量 | 覆盖 |
| --- | --- | --- |
| 业务内核 `test_domain` | 19 | 状态机 10 条迁移、非法迁移拒绝、岗位越权拒绝、守卫（六项检查/报修原因/返工说明）、闸门与替代房、时效与 P90、事件只追加 |
| 知识库 `TestKnowledgeBase` | 5 | 种子完整性、切片边界、口径召回、增删、重建幂等 |
| 工具与助手 `TestTools`/`TestAgentFallback` | 11 | 闸门读取、可售排除已清扫、越权提案被拦、提案生命周期、五类意图回答、会话落库 |
| 护栏 `TestValidation` | 6 | 假引用、真引用、指标数字不一致、未查房号、引号内示例豁免、无动作却声称已执行 |

跑法：`python -m unittest discover -s tests -v`（约 40 秒，不需要模型密钥）。

### 5.3 与真实系统对接（本期不做，接口已留）

| 对接对象 | 替换点 | 说明 |
| --- | --- | --- |
| PMS / 房态主数据 | `api/rooms.py` 的读路径 | 现在读本地表，改成读 PMS 适配器；写路径仍走 `transition()` |
| 门锁 | `check_in` 迁移后置钩子 | 开房成功后发卡，失败则回滚房态 |
| 工单系统 | `tasks` 表写入处 | 换成一个 `TaskSink` 接口，可落本地也可推送 |
| 企业微信 / 短信 | `handover` 提交后 | 交接摘要与超时提醒外发 |

### 5.4 下一步优先级（建议）

1. **接真实 PMS 只读**：把房态来源换成真数据，代理指标立刻有验收意义；
2. **补「入住等待」实测**：在大堂加一个扫码取号/叫号，才能验证 38 → 15 是否成立；
3. **知识库扩到 20 篇**：把客诉高频问题、特殊情况处置补进去，减少转人工；
4. **助手加「相似历史」**：用 `interventions` + `room_events` 做「上次这种情况怎么处理的」检索，把老师傅经验变成可查资产。
